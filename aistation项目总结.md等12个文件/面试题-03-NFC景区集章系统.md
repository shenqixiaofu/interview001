# 1. 请你介绍一下 NFC 景区集章系统这个项目，你主要做了什么？

参考答案：
这个项目是一个偏互动营销和文旅场景的全栈项目，目标是通过 NFC 标签触达用户，让用户在景区里完成徽章收集、打卡和集章活动，同时后台可以查看数据和运营效果。  
项目分成三块：用户端、管理端和 FastAPI 后端。  
用户端主要负责 NFC 解锁、徽章点亮、活动展示和互动体验；管理端负责景区配置、徽章管理、标签管理、打卡记录和运营统计；后端负责核心业务模型、接口和统计逻辑。  
我参与的是比较完整的全栈开发，包括前端页面、后端接口以及打卡漏斗统计这类功能。

# 2. 这个项目的业务闭环是什么？

参考答案：
我会把它总结成“触达 - 互动 - 转化 - 复盘”四步。  
第一步，用户在线下通过 NFC 标签被触达。  
第二步，用户进入页面后完成徽章解锁、收集和浏览。  
第三步，用户持续参与，完成打卡、集齐徽章等核心互动。  
第四步，后台通过统计数据复盘哪些标签更受欢迎、哪些点位转化更高、哪些环节有流失。  
所以它不是单纯做一个小游戏，而是一个可以被运营使用的数据化活动系统。

# 3. 为什么这个项目适合用 NFC，而不是普通二维码？

参考答案：
NFC 和二维码相比，最大的差异在交互体验。  
二维码需要用户主动扫码，而 NFC 更接近“碰一下就进入”，路径更短，互动感更强。  
对于景区这种线下场景，NFC 更有沉浸感，也更容易和“打卡”“收集徽章”这种玩法结合。  
当然它的推广成本会比二维码高一些，因为需要布置标签，但如果重点是活动体验和线下互动感，NFC 是更合适的。

# 4. 用户从碰到 NFC 到徽章点亮，这条链路是怎样的？

参考答案：
用户碰到 NFC 标签以后，会跳转到带参数的页面链接，比如 URL 里会带标签编号或解锁参数。  
前端页面打开后，会先读取这个参数，然后调用后端接口验证标签是否合法、是否属于当前景区、是否对应某个徽章。  
验证通过以后，后端记录一次触达或打卡行为，并返回当前徽章、用户进度等信息。  
前端根据返回结果播放解锁动画、点亮徽章，并更新用户当前收集进度。  
如果这次触发已经完成全部徽章收集，前端还可以继续触发庆祝动画或证书展示。

# 5. 为什么这个项目里还要专门做管理端？

参考答案：
因为景区活动不是做完就结束了，它是要被运营同学长期使用的。  
管理端的意义在于让非研发也能完成活动配置和数据查看。  
比如景区要新增徽章、调整点位、批量生成 NFC 标签、查看某个标签的热度、重置用户进度，这些都需要后台支撑。  
如果没有管理端，所有配置都得靠研发改库或改代码，那这个项目就很难长期运营。

# 6. 后端为什么适合用 FastAPI？

参考答案：
因为这个项目虽然业务不算特别复杂，但接口比较多，而且需要快速迭代。  
FastAPI 的优势是开发效率高，参数校验和接口文档比较清晰，适合这种中小型前后端分离项目。  
另外它本身也支持异步，后续如果要扩展文件上传、统计分析或者更多并发 IO 场景，也比较顺手。  
对这个项目来说，FastAPI 是一个开发效率和维护成本都比较平衡的选择。

# 7. 你们为什么要设计“碰一碰 -> 打卡 -> 集齐”这个漏斗？

参考答案：
因为项目的目标不只是“展示功能做出来”，而是要回答运营问题。  
比如标签有没有被触达？用户碰了以后有没有完成打卡？完成打卡以后有没有继续把全部徽章集齐？  
这其实就是一个很典型的业务漏斗。  
通过这个漏斗，运营能看出问题到底出在哪一层，是点位没吸引人、页面转化差，还是活动设计本身太难。

# 8. 为什么要区分“原始触达次数”和“有效触达次数”？

参考答案：
因为 NFC 场景里重复触碰和误触很常见。  
如果只统计总触达次数，很可能一个用户连续碰几次就把数据冲高了，运营看到的数据会失真。  
所以一般要把“原始次数”和“去重后的有效次数”分开。  
这样既能看到设备真实触发频率，也能更接近真实用户行为。

# 9. 你们为什么用了 30 秒去重？

参考答案：
30 秒去重本质上是一个业务口径，不是绝对标准。  
设计这个口径的目的，是尽量过滤同一用户在短时间内的重复触碰，避免误触和刷数据。  
30 秒通常足够覆盖用户连续碰两三次的场景，同时又不会把真正过一段时间再次参与的行为全部吞掉。  
如果后续运营反馈说时间太长或太短，其实也可以继续调整，但核心思路就是要有一个合理的去重窗口。

# 10. 这个去重逻辑为什么不能只放前端做？

参考答案：
前端只能优化体验，不能作为最终统计口径。  
因为前端很容易被绕过，比如换浏览器、清缓存、直接调接口，或者网络波动导致状态异常。  
真正的统计逻辑必须以后端为准，后端根据设备标识、时间窗口和标签编号来统一判定这次是否算有效触达。  
这样数据口径才稳定，也方便做后台统计和复盘。

# 11. 设备 ID 在这个项目里为什么重要？

参考答案：
因为项目需要知道“是不是同一个用户设备”。  
在没有完整账号体系的情况下，设备 ID 往往是一个比较现实的去重依据。  
比如统计有效触达、区分参与用户数、判断是否重复打卡，都需要一个能相对稳定代表用户设备的标识。  
当然设备 ID 不是绝对可靠，但在这类活动项目里，它通常已经够用，而且实现成本低。

# 12. 如果面试官问：设备 ID 会不会不准？你怎么答？

参考答案：
会有误差，但要看业务场景接受度。  
比如用户换设备、清缓存、某些浏览器限制设备标识，这些都会影响准确性。  
但对于景区互动活动这类场景，重点通常不是金融级别精确识别，而是得到一个足够可用的运营口径。  
所以设备 ID 可以作为一个低成本方案。  
如果未来业务要求更严，也可以叠加登录态、手机号、会员 ID 等更稳定的用户标识。

# 13. 用户端为什么要做很多动画和音效？

参考答案：
因为这个项目的核心不是管理系统，而是线下活动体验。  
如果用户碰一下 NFC 后，只看到一个普通页面提示“成功”，互动感会很弱。  
徽章点亮、音效、集齐庆祝这些设计，其实是在放大“收集”和“成就感”，提升用户持续参与意愿。  
所以这些动画不是装饰，而是和业务目标直接相关的体验设计。

# 14. 如果动画很多，前端性能要注意什么？

参考答案：
第一，动画不要全靠频繁重排重绘，尽量优先用 transform、opacity 这些更轻量的方式。  
第二，资源像图片、音频要控制大小，避免页面初次加载过重。  
第三，动画和业务逻辑最好解耦，防止一个接口慢就把整个动画节奏拖死。  
第四，移动端要注意不同机型兼容性，避免高端机流畅、低端机卡顿。  
对这种活动页来说，流畅度本身就是体验的一部分。

# 15. 管理端的统计看板里，你觉得最有价值的指标是什么？

参考答案：
我觉得最核心的是三类。  
第一类是触达类，比如总触达、有效触达、热门标签。  
第二类是转化类，比如触达后完成打卡的转化率、打卡后集齐徽章的完成率。  
第三类是用户类，比如参与用户数、完成用户数。  
因为运营最关心的是“有没有人来”“来了以后有没有继续玩”“最后有没有完成活动”，这三层正好对应项目价值。

# 16. 这个项目里你觉得最难讲清楚的技术点是什么？

参考答案：
我觉得不是某一个框架 API，而是“业务口径”和“技术实现”怎么对齐。  
比如什么叫一次有效触达、什么叫参与用户、什么时候算完成收集，这些都不是纯技术问题，而是业务定义。  
技术要做的是把这些业务定义稳定地落到数据库结构、接口返回和统计口径里。  
所以真正难的是让数据能反映真实业务，而不是单纯把页面和接口写出来。

# 17. 如果让你继续优化这个项目，你会先做什么？

参考答案：
我会优先做两件事。  
第一，继续优化统计维度，比如按景区、按标签、按时间段拆开看，提升运营复盘能力。  
第二，增强用户侧活动体验，比如把集章、抽奖、任务体系和用户画像串起来，做更完整的活动闭环。  
因为这个项目本质上是一个线下互动运营系统，后续最有价值的方向还是“数据更清楚”和“体验更有吸引力”。

# 18. 如果面试官问：这个项目是不是就是个小游戏？你怎么答？

参考答案：
我会说它表面上有活动玩法，但底层其实是一个完整的业务系统。  
它有用户端、管理端、后端、数据模型、统计口径和运营看板，不是只做一个动画页面。  
小游戏只是用户看到的那一层，真正的价值在于它把线下触达、用户互动和后台运营数据串起来了。  
所以它更准确的定位应该是“景区互动营销系统”，而不只是小游戏。
