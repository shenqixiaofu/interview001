# 1. 请你介绍一下趣行智旅 SaaS 系统这个项目，你主要做了什么？

参考答案：
这个项目本质上是一个文旅行业的 SaaS 系统，交付形态比较多，包含管理员后台、酒店端小程序、景区端小程序等。  
管理端主要负责配置、内容和运营类能力，前端技术栈是 Vue 3、Vben、Ant Design Vue、pnpm monorepo。  
小程序端主要基于 uni-app x / UTS 来做，酒店端有微信登录、房间绑定、AI 对话、反馈、打卡、抽奖、在线客服、前台服务这些功能，景区端则围绕导览、AI 讲解、在线客服、反馈和内容解锁展开。  
我参与的重点是多端业务开发和联调，尤其是小程序核心页面、WebSocket 实时消息、会话状态同步，以及前后端接口口径统一。

# 2. 这个项目为什么适合用 SaaS 方式来做？

参考答案：
因为酒店和景区这类业务有很强的共性。  
比如首页配置、反馈、客服、导览、会员、营销活动、内容管理，这些能力很多商家都需要，只是展示内容和部分业务规则不同。  
如果每个客户都单独做一套系统，成本高、维护也重；SaaS 的好处是把共性的底座能力统一建设起来，再通过租户、业态、配置去做差异化。  
所以它更适合做成一个多租户、多业态的系统。

# 3. 你怎么理解这个项目里的“多租户”和“多业态”？

参考答案：
多租户是指同一套系统同时服务多个商家或客户，每个租户的数据和配置要隔离。  
多业态是指同样的底座能力要服务不同业务类型，比如酒店和景区虽然都属于文旅，但业务对象和页面心智不一样。  
所以这个项目里不只是“租户隔离”，还要处理“酒店上下文”和“景区上下文”的切换。  
也就是说，一套技术底座支撑多个租户，同时还要支撑多种行业场景。

# 4. 为什么小程序端用了 uni-app x / UTS，而不是普通 H5 或纯原生？

参考答案：
核心原因是交付效率和多端复用。  
小程序业务通常页面多、迭代快，如果完全原生做，开发和维护成本会比较高。  
uni-app x / UTS 的优势是可以用接近 Vue 的方式开发，同时兼顾多端复用，适合这种业务型项目。  
另外团队里如果已经有 Vue 技术栈积累，用 uni-app x 会更顺手，前后端联调效率也更高。

# 5. 这个项目里为什么会有很多“ownerId / ownerType”这种统一口径？

参考答案：
因为它要同时服务酒店和景区这样的多业态。  
如果接口完全按 `hotelId` 去设计，那当景区端也想复用同样的能力时，就会出现语义不匹配的问题。  
所以更通用的做法是抽成 `ownerType + ownerId`，也就是“谁拥有这份业务数据”。  
这样后端底层可以统一处理，前端根据当前业态传不同的 owner 信息，就能复用更多能力。

# 6. 你在这个项目里做过哪些 AI 相关能力？

参考答案：
主要是业务侧的 AI 能力接入，而不是底层模型平台研发。  
比如酒店端和景区端的小程序里，都有 AI 对话、在线客服、反馈回复等功能。  
我更关注的是前端交互链路，比如如何展示流式回答、如何处理 WebSocket 消息、如何同步会话状态、如何在业务页面里接入 AI 入口，以及如何和登录态、上下文、用户身份打通。  
所以这个项目里的 AI 更偏“业务落地”，不是单独做模型平台。

# 7. 这里为什么要用 WebSocket，而不是每次发 HTTP 请求轮询？

参考答案：
因为 AI 对话和客服消息都比较适合实时推送。  
如果每次都用 HTTP 轮询，不仅请求频率高，而且用户看到消息会有延迟。  
WebSocket 建立连接后，后端可以持续推送回答内容、客服接管状态、系统通知这些事件，体验更接近即时通信。  
另外像“AI 回复中”“人工已接管”“人工已结束服务”这种状态，本来就更适合事件驱动模型。

# 8. WebSocket 断开重连一般怎么设计？

参考答案：
前端一般会维护连接状态，比如连接中、已连接、已断开。  
如果连接异常断开，可以根据页面活跃状态和业务场景决定是否自动重连。  
重连时要注意两点：一是不要无限重连，要有限次和退避策略；二是重连后要恢复会话上下文，比如当前会话 ID、用户信息、页面标识。  
如果后端推送的消息带有会话 ID 或 requestId，前端还要做校验，避免把旧连接的消息误渲染到当前会话里。

# 9. 什么叫“人工接管”，前端一般怎么配合？

参考答案：
人工接管通常是指 AI 先回复，但当问题复杂或用户需要人工时，由人工客服接手当前会话。  
前端要做的事情一般有几个：  
第一，识别接管状态，比如显示“人工客服已接入”。  
第二，在 UI 上区分 AI 消息和人工消息。  
第三，某些情况下切换输入提示或交互模式，比如不再展示 AI 的建议语。  
第四，如果人工服务结束，还要恢复回 AI 模式。  
本质上这是一个会话状态机问题，不只是渲染文本。

# 10. 房间绑定这种功能，你觉得技术上要注意什么？

参考答案：
房间绑定表面上是一个表单提交，但它其实和用户身份、租户上下文、业务权限是相关联的。  
比如用户必须先登录，绑定时要明确当前酒店上下文，后端还要校验房号、手机号、验证码或者其他业务凭证是否匹配。  
绑定成功以后，很多后续能力都会依赖这个状态，比如获取当前房间服务、WiFi、住中服务等，所以绑定状态一定要能稳定地被前后端感知和持久化。

# 11. 登录态在小程序里一般怎么处理？

参考答案：
常见方案还是 access token + refresh token。  
前端登录成功后，把 token 安全地缓存下来，请求时统一带上。  
当 access token 过期时，用 refresh token 去刷新。  
小程序端要特别注意的是登录态和上下文状态不要混在一起，比如 token、租户信息、酒店/景区上下文、房间绑定状态，最好分别管理。  
这样问题定位和状态恢复都会更清楚。

# 12. 这个项目里为什么接口联调会比较复杂？

参考答案：
因为它不是单一前端。  
一个需求可能同时影响管理员后台、小程序端和后端，而且还涉及不同业态。  
比如同样是反馈功能，后台要看列表、审核和回复，小程序端要提交和查看结果，后端要统一数据结构和权限逻辑。  
如果接口口径不统一，就会出现小程序一个字段名、后台一个字段名、后端再兼容一套旧字段，这会让长期维护很累。  
所以我会把“统一接口口径”看成这类项目很重要的一部分工作。

# 13. 管理后台为什么会用 Vben 这种中后台框架？

参考答案：
因为这类后台页面很多都是标准中后台能力，比如表格、表单、权限、菜单、布局、路由、字典、上传、弹窗这些。  
如果从零开始搭，成本高而且不稳定。  
Vben 这类框架的价值在于把通用中后台底座做好，团队可以把精力更多放在业务模块上。  
所以它更适合这种“后台很多、业务迭代快”的场景。

# 14. 你怎么理解 monorepo 在这个项目里的价值？

参考答案：
monorepo 的价值在于统一管理。  
如果后台、公共组件、工具方法、配置文件都拆成多个仓库，依赖同步和版本管理会很麻烦。  
monorepo 可以把共享能力放在一起维护，比如公共请求层、类型定义、工具函数、组件包。  
对于多端和多模块共存的项目来说，它更适合做统一规范和复用。

# 15. 如果面试官问：你这个项目最大的技术难点是什么？你怎么答？

参考答案：
我会说这个项目真正的难点不是某一个 API，而是“多端 + 多业态 + 实时交互”的组合复杂度。  
单看某一个页面可能并不难，但当一个能力同时涉及后台、小程序、AI 对话、WebSocket、用户身份、租户上下文时，系统复杂度会上来。  
所以我理解这个项目的技术难点主要在于状态管理、接口统一、上下文切换和实时消息链路，而不只是页面开发本身。

# 16. 这个项目里如果让你继续优化，你最想做什么？

参考答案：
我会优先从两方面做。  
第一是平台化，把当前酒店端和景区端重复的能力再抽一层，减少前端重复实现。  
第二是 AI 侧继续增强，比如把现在的 AI 对话能力和知识库、客服、工单系统打通，往更强的 Agent 应用演进。  
因为从业务角度看，这类文旅 SaaS 后续很适合做“AI 助手 + 业务执行”的能力。
