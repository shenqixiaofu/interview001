# 1. FastAPI 和 Flask、Django 相比，你为什么会选 FastAPI？

参考答案：
我会优先从项目类型来看。  
如果是前后端分离、接口较多、需要参数校验、异步 IO、WebSocket 这些能力，FastAPI 会比较合适。  
它和 Pydantic 结合得很好，接口定义、参数校验、返回结构都比较清晰，联调效率高。  
相比 Flask，FastAPI 的工程化和类型约束更强一些；相比 Django，它更轻，做纯 API 服务时负担更小。  
所以我会把 FastAPI 理解成“适合现代 API 服务和 AI 应用后端”的框架。

# 2. FastAPI 里的异步什么时候有价值？是不是所有接口都应该写 async？

参考答案：
不是所有接口都应该盲目写 async。  
异步真正有价值的场景，通常是大量 IO 操作，比如调外部模型接口、访问 Redis、文件上传下载、WebSocket 长连接、数据库异步查询。  
如果一个接口主要是 CPU 计算，或者底层库本身就是同步阻塞的，那写成 async 收益不一定大。  
所以关键不是“语法上有没有 async”，而是看整个调用链是不是异步友好。

# 3. SQLAlchemy 你怎么理解？

参考答案：
我把 SQLAlchemy 理解成 Python 里比较成熟的 ORM 和数据库抽象层。  
它的价值在于把数据库表结构、查询语句和业务代码做了比较好的分层，方便维护。  
简单 CRUD 场景下能提高开发效率，复杂查询场景下也保留了足够灵活性。  
对我来说，常见使用方式就是定义模型、写 CRUD、配合 service 层做业务封装。

# 4. Redis 在 Web 项目里常见用途有哪些？

参考答案：
最常见的还是缓存、登录态、限流和短时状态存储。  
再往业务侧走，Redis 也很适合做任务状态管理、简单消息协调、分布式锁、热点数据缓存。  
如果是 AI 项目，还可能用于排队任务、会话短时状态、流式对话控制等场景。  
所以 Redis 不只是“缓存数据库”，它更像一个高性能的运行时辅助组件。

# 5. WebSocket 和 HTTP 的核心区别是什么？

参考答案：
HTTP 更适合请求一次、响应一次的场景，是典型的短连接请求模型。  
WebSocket 在握手建立之后，可以保持长连接，支持服务端和客户端双向通信。  
所以像聊天、通知、实时状态同步这类场景，更适合 WebSocket。  
而普通查询、表单提交、分页列表这些，还是 HTTP 更合适。

# 6. SSE 和 WebSocket 你怎么选？

参考答案：
如果场景只是服务端单向往前端推数据，比如简单流式文本、通知流，SSE 会更轻量。  
如果场景需要双向通信，比如实时聊天、停止生成、状态同步、心跳保活，那 WebSocket 更合适。  
所以不是谁更高级，而是看业务到底要不要双向交互。

# 7. 什么是 RAG？

参考答案：
RAG 是 Retrieval-Augmented Generation，也就是检索增强生成。  
简单理解，就是先从知识库里检索相关内容，再把检索结果和用户问题一起交给大模型生成答案。  
它的核心价值是让模型回答建立在外部知识上，而不是只靠参数记忆。  
这样可以降低幻觉，也能让模型回答私有知识。

# 8. 一个完整的 RAG 流程有哪些步骤？

参考答案：
通常可以拆成离线和在线两部分。  
离线是文档上传、解析、切片、向量化、写入向量索引。  
在线是用户提问、问题向量化、检索相关片段、拼接 Prompt、模型生成答案。  
所以 RAG 的关键不是“把文档传上去”，而是“先准备知识，再在问答时动态检索”。

# 9. 为什么 RAG 能降低幻觉？

参考答案：
因为它给模型提供了当前问题相关的外部证据。  
如果没有 RAG，模型很多时候只能根据自己训练时学到的内容去猜。  
有了 RAG，模型在回答时会参考检索到的文档片段，这样回答更容易落在真实资料上。  
当然它不能完全消灭幻觉，但能明显降低“胡编”的概率。

# 10. 向量检索和关键词检索有什么区别？

参考答案：
关键词检索更依赖词面匹配，适合术语明确、关键词固定的场景。  
向量检索更强调语义相似度，即使用户问题和文档原文用词不完全一样，也有机会召回相关内容。  
所以向量检索在自然语言问答里更常见。  
但很多实际系统里不会只用一种，往往会把语义检索和关键词规则结合起来。

# 11. Chunk 切片为什么要做 overlap？

参考答案：
因为文档内容很多时候不是天然独立的，前后段落会有上下文关联。  
如果完全硬切，可能一个定义在上一段，结论在下一段，检索出来后语义就断了。  
加 overlap 的目的就是在相邻切片之间保留一部分重叠内容，降低上下文断裂的风险。  
这是提升检索质量的一个常见手段。

# 12. 向量库为什么不能直接用数据库表替代？

参考答案：
数据库当然可以存 embedding，但“存下来”和“高效做近似向量检索”不是一回事。  
向量库的价值在于针对高维向量相似度搜索做了更合适的索引和检索优化。  
如果只是少量数据或者 demo，直接存在表里也能跑；但一旦文档量大起来，专门的向量索引会更合适。  
所以本质上是性能和检索能力的考虑。

# 13. 你怎么理解 Prompt 设计？

参考答案：
Prompt 设计本质上是在控制模型输入结构，让模型更稳定地按预期输出。  
比如定义角色、限定回答风格、约束输出格式、要求引用知识、不允许编造。  
在业务系统里，Prompt 不是“写一句神奇咒语”，而是系统提示词、用户输入、上下文知识、工具结果这些内容的组合设计。  
它更像一种输入编排能力。

# 14. OpenAI Compatible API 指的是什么？

参考答案：
就是很多模型服务虽然底层不是 OpenAI，但它们会兼容 OpenAI 的接口协议。  
这样前端或后端在接入时，可以用相似的请求格式和 SDK 调用不同模型服务。  
这种方式的好处是切换供应商成本更低，系统设计也更统一。  
很多本地模型服务、云上模型平台都会提供这种兼容层。

# 15. 为什么做 AI 对话时要支持流式输出？

参考答案：
主要还是用户体验。  
如果模型思考 10 秒钟，前端一直没反应，用户会觉得系统卡了。  
流式输出可以让用户更早看到模型开始返回内容，感知延迟更低。  
另外对于较长回答，流式展示比一次性整块返回更自然，也更像真实对话。

# 16. 你怎么理解前端状态管理？

参考答案：
前端状态管理不是为了“必须上某个库”，而是为了把页面共享状态、会话状态、用户状态组织清楚。  
像登录态、菜单权限、当前会话、选中的文档、当前模型，这些如果全散在组件里，后期很难维护。  
像 Pinia 这种状态库的价值就是让全局共享状态更清晰，同时便于调试和持久化。

# 17. Vue 3 和 Vue 2 相比，你觉得最重要的变化是什么？

参考答案：
我觉得最重要的是组合式 API 带来的组织方式变化。  
复杂页面里，相关逻辑可以按功能拆到一起，而不是被 data、methods、computed 分散。  
另外 Vue 3 在类型支持、性能和生态工具链上也更现代一些，更适合 TypeScript 开发。  
所以对中大型项目来说，可维护性提升比较明显。

# 18. 你怎么理解前后端分离项目里的“接口口径统一”？

参考答案：
就是接口字段、状态码、分页结构、业务标识这些要有统一规范。  
如果同类接口每个模块都自己定义一套字段名和结构，前端适配成本会很高，后期维护也容易出问题。  
所以接口口径统一其实是在降低系统复杂度，让前后端协作更顺。

# 19. Docker 在你的项目里主要价值是什么？

参考答案：
我会把 Docker 理解成“让环境更一致”。  
比如后端依赖、运行命令、服务组合、部署方式，如果每个人手工配一套，环境问题会很多。  
Docker 可以把运行环境标准化，降低“我本地能跑、你那里跑不起来”的情况。  
对于前后端分离项目或者带 Redis、数据库的项目，Docker 也更方便做一键部署和环境复现。

# 20. 如果面试官问：你现在偏全栈，为什么还投 Agent 方向？

参考答案：
因为我理解 Agent 应用工程本身就不是纯算法岗位，它很强调工程落地。  
一个真实 Agent 系统往往要把前端交互、后端服务、模型接入、知识库、工具调用、任务状态和业务流程串起来。  
我现在的优势正好是多端业务开发和系统落地能力，再往上叠加 RAG、Prompt、工具调用这些能力，我认为和 Agent 应用工程是很匹配的。  
所以我的路径不是“从零转行”，而是“从业务全栈向 AI 应用全栈延伸”。
