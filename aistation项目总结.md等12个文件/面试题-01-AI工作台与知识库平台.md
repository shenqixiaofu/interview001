# 1. 请你介绍一下 AI 工作台与企业知识库平台这个项目，你主要做了什么？

参考答案：
这个项目本质上是一个 AI 工作台，核心能力包括 AI 对话、统一文档中心、知识库检索增强问答、模型管理、会话记忆，以及一些本地 AI 任务，比如音视频转写、文档转换和语音合成。  
技术栈上，后端是 FastAPI + SQLAlchemy + Redis + WebSocket，前端是 Vue3 + TypeScript + Element Plus，AI 侧接了 OpenAI Compatible 接口，同时用了 LangChain、Agno 和 Chroma 来处理检索增强这部分能力。  
我重点关注的是前后端联调和 AI 对话链路，包括聊天页面、WebSocket 流式消息展示、文档挂载、模型切换、会话管理，以及知识库问答相关的前端交互。另外我也会关注后端的整体链路设计，
比如文档上传后的解析、切片、向量化和检索流程，以及聊天时如何把挂载文档和会话上下文一起送给模型。

# 2. 用户在这个平台里提一个问题，到模型最终返回答案，中间完整链路是什么？

参考答案：
我会把这条链路拆成五步。  
第一步，用户在前端输入问题，前端会带上当前会话 ID、选中的模型 ID、挂载的文档 ID 等信息，通过 WebSocket 发起一次流式对话请求。  
第二步，后端拿到请求以后，会先解析当前会话配置，包括当前使用的模型、当前挂载的文档、当前会话历史以及智能体配置。  
第三步，如果当前这次问答挂载了文档，后端会先走知识检索流程，也就是把用户问题做 embedding，然后在向量库里检索相关切片，必要时还会做一定的筛选和补充。  
第四步，后端把系统提示词、会话历史、用户当前问题、检索出来的文档片段，一起组织成最终 Prompt，再交给模型生成答案。  
第五步，模型返回 token 以后，后端通过 WebSocket 持续把增量内容推送给前端，前端实时渲染，结束后再把整轮消息和状态持久化到会话里。

# 3. 为什么这里选 WebSocket 做流式对话，而不是普通 HTTP？

参考答案：
普通 HTTP 更适合请求一次、返回一次的场景，但聊天尤其是大模型流式输出场景，本质上是一个长连接持续推送的过程。  
如果用普通 HTTP 轮询，前端需要不断发请求拿增量内容，开销大，实时性也差。  
WebSocket 的优势是连接建立后可以双向通信，后端能持续推 token 给前端，前端也能在同一条链路上做停止生成、心跳保活、状态同步这些操作。  
对聊天产品来说，WebSocket 的交互模型更接近真实对话。  
如果只看单向推送，其实 SSE 也可以做流式输出，但 WebSocket 更灵活，因为它不仅能收模型输出，还能承载用户主动中断、重连恢复、状态通知等双向场景。

# 4. 那 WebSocket 和 SSE 的区别你怎么说？

参考答案：
SSE 是服务端单向推送，前端发起请求后，后端持续往前端推数据，适合消息流、通知流这种场景。  
WebSocket 是双向通信，客户端和服务端都可以主动发消息。  
如果只是简单做流式文本返回，SSE 会更轻量；但如果要支持停止生成、断线重连后的状态同步、会话控制、心跳这些能力，WebSocket 更合适。  
所以我的理解是，SSE 偏“流式展示”，WebSocket 偏“对话交互”。

# 5. 文档上传后，为什么不能直接整篇塞给模型，而要做解析、切片、向量化？

参考答案：
主要有三个原因。  
第一，整篇文档直接塞模型会很容易超过上下文窗口，尤其是 PDF、Word、会议纪要这类长文档。  
第二，就算没超，整篇塞进去也会带来很多无关信息，既增加 token 成本，也会干扰模型回答。  
第三，知识库问答的目标不是让模型读完整个文档，而是让模型快速拿到和当前问题最相关的内容，所以需要先把文档切成小块，再通过向量检索找出相关片段。  
这样做本质上是在控制上下文质量，让模型“少看但看准”。

# 6. 你理解的 RAG 流程是什么？

参考答案：
RAG 一般就是 Retrieval-Augmented Generation，也就是检索增强生成。  
完整流程可以概括成两段。  
离线段是文档入库：上传文档、解析文本、切片、做 embedding、写入向量索引。  
在线段是用户问答：用户提问、问题向量化、在向量库里检索相关切片、把切片和问题一起拼进 Prompt，再让模型生成答案。  
所以 RAG 不是“上传文档就结束了”，而是“文档先准备好，问答时再动态检索相关内容”。

# 7. 切片为什么重要？切片大小一般怎么定？

参考答案：
切片的核心目标是平衡“语义完整性”和“检索精度”。  
切得太大，会带入很多无关内容，检索出来的结果不够精准。  
切得太小，又会导致语义不完整，模型拿到片段以后可能无法理解上下文。  
一般会按段落、标题、句子长度做切分，也可能加 overlap，也就是相邻切片保留一部分重叠内容，避免上下文断裂。  
实际大小没有绝对值，通常要结合文档类型、模型上下文长度和检索效果去调。  
比如制度类文档可能按条款切，会议纪要可能按议题切，PDF 长文可能按固定 token 数加重叠切。

# 8. 向量检索的效果怎么评估？

参考答案：
我会从线上和线下两个角度看。  
线下可以准备一批问答样本，看检索出来的 TopK 结果里是否覆盖正确答案，也就是看召回率、命中率。  
线上更关注真实用户提问后的回答质量，比如用户是否追问、是否切换人工、是否点踩、是否反复改写问题。  
如果进一步做细一点，还可以看“检索到了但模型没答好”和“根本没检索到”这两类问题，因为它们对应的优化方向不一样。  
前者可能是 Prompt 拼接或回答组织问题，后者更可能是切片、embedding 模型、索引或召回策略问题。

# 9. 如果知识库没检索到有效内容，你会怎么处理？

参考答案：
这种情况不能硬编。  
比较稳的做法是，后端在检索阶段设定一个最低相关度阈值，如果没有达到阈值的结果，就不要把低质量片段硬塞给模型。  
这时候要么直接走纯模型回答，但明确告诉模型“没有可靠知识依据，不要编造”；要么直接返回“当前知识库中没有检索到足够信息，请补充问题或联系人工”。  
如果是企业知识库场景，我会更偏向保守处理，因为胡答的风险比答不上更大。

# 10. 聊天时为什么要支持“挂载文档”？

参考答案：
挂载文档的价值在于缩小检索范围，提高回答的确定性。  
如果用户明确只想围绕某几个文档问问题，那就没必要在整个知识库里全局检索。  
挂载之后，后端可以只在选中的文档集合里做 embedding 检索，这样召回更准，噪音更少。  
另外从产品角度看，挂载文档也能让用户知道“这次回答是基于哪些资料来的”，可解释性会更强。

# 11. 会话为什么要持久化，不能只放前端？

参考答案：
只放前端的问题很多。  
第一，用户刷新页面、换浏览器、换设备以后，聊天记录就丢了。  
第二，如果要支持后台统计、问题追溯、内容审核、人工接管，就必须有后端持久化。  
第三，知识库问答往往不只是展示文本，还会绑定模型、挂载文档、会话摘要、时间戳等信息，这些都更适合放在服务端统一管理。  
所以前端本地缓存可以作为体验优化，但真正的会话状态还是应该以后端持久化为主。

# 12. 如果本地模型很慢或者繁忙，你会怎么处理？

参考答案：
这个问题要分两层。  
第一层是运行时层面，要有限流、排队、超时、取消、重试这些机制，否则一旦多个任务一起上来，本地算力很容易打满。  
第二层是产品层面，要把状态明确告诉用户，比如“排队中”“处理中”“超时，请稍后重试”。  
如果是聊天场景，还要支持用户主动停止当前回答。  
如果本地模型长期繁忙，也可以设计成本地模型和远程模型的双路策略，优先本地，失败后根据策略切到在线模型。

# 13. 用户点“停止生成”时，前后端一般怎么设计？

参考答案：
前端这边需要记录当前请求 ID 或会话上下文，点击停止后，通过 WebSocket 给后端发一个停止事件。  
后端收到以后，要能找到当前这次生成任务，并把任务状态改成取消中或已取消，同时尽量中断对模型的下游读取。  
前端收到最终状态后，把输入框和发送按钮恢复。  
如果做得更完整，还要避免“用户已经点停了，但后端最后又推了一段旧 token 回来”的问题，所以通常还会加请求 ID 校验或 generation 标识。

# 14. 你怎么理解“会话记忆”？

参考答案：
我理解会话记忆不是单纯保存历史消息，而是让模型在多轮对话里能延续上下文。  
最简单的是直接拼接最近几轮消息，但这样 token 成本会越来越高。  
更常见的做法是保留近几轮原始对话，再加上摘要记忆，也就是把更早的对话压缩成一段总结。  
这样既保留上下文，又控制成本。  
如果以后做得更复杂，还可以做用户长期偏好、任务状态记忆，但那已经超出普通聊天记忆范畴了。

# 15. 你这个项目里，哪些部分算 RAG，哪些部分还不能算真正的 Agent？

参考答案：
RAG 的部分主要是统一文档中心、文档解析切片、向量化入库、聊天时的检索增强问答、文档挂载检索这些。  
这些能力已经具备“知识检索 + 大模型生成”的闭环，所以可以算标准 RAG 应用。  
但它还不能完全算真正的 Agent，原因是当前更偏“知识问答工作台”，而不是“基于目标自动规划并调用工具执行任务”。  
如果没有明确的工具调用、任务规划、步骤执行、结果回写这些能力，那它更准确的定位还是 AI 工作台或 RAG 平台，而不是成熟 Agent 系统。

# 16. 如果继续往 Agent 方向演进，你下一步最想加什么？

参考答案：
我会优先加三类能力。  
第一类是 Tool Calling，也就是让模型不只回答，还能调用外部工具，比如查询数据库、创建工单、调用天气接口、触发企业内部服务。  
第二类是工作流编排，让复杂任务可以拆成多个节点执行，而不是所有逻辑都塞进一次对话。  
第三类是评估和观测能力，比如记录命中率、失败原因、用户反馈、工具调用成功率。  
因为真正的 Agent 不是“会聊天”，而是“会基于目标调用能力完成任务”。

# 17. 如果面试官追问 MCP，你怎么回答？

参考答案：
MCP 我理解成一种模型和外部工具/资源之间更标准化的接入协议。  
它的价值在于把工具调用、资源暴露、上下文注入这类事情做得更统一，而不是每接一个工具都自己写一套私有协议。  
如果平台以后扩展到更多内部工具，比如知识检索、工单系统、CRM、报表系统，那用 MCP 这种标准化方式会更容易扩展。  
就我当前项目理解，MCP 更适合作为 Agent 平台演进时的工具接入层，而不是知识库问答阶段的第一优先级。

# 18. FastAPI 为什么适合做这个项目？

参考答案：
我觉得主要有几个原因。  
第一，FastAPI 本身异步支持比较自然，适合 WebSocket、长连接、并发 IO 这类场景。  
第二，它和 Pydantic 结合得很好，接口参数校验、响应结构定义都比较清晰，前后端联调成本低。  
第三，AI 相关场景往往需要接很多外部服务，比如模型接口、文档解析、向量化服务、本地运行时，这些都比较适合用 FastAPI 来组织。  
第四，文档自动生成也比较方便，开发阶段调试效率高。

# 19. Redis 在这个项目里可能承担什么角色？

参考答案：
Redis 在这类项目里通常不会只做缓存。  
一方面它可以存登录态、限流、系统配置缓存。  
另一方面在 AI 场景里，它也很适合做任务状态管理、短时会话状态、排队调度或者分布式锁。  
如果本地算力任务比较多，比如转写、TTS、向量化这类重任务，Redis 也很适合参与任务调度链路。  
所以它在这个项目里更像一个轻量级运行时协调组件。

# 20. 讲一下你理解的“统一文档中心”为什么比“多个知识库切换”更适合当前产品？

参考答案：
我理解这是一种产品心智设计。  
如果产品目标是让普通用户快速上传资料并提问，那“文档中心”心智会比“知识库管理”更简单。  
用户不需要先理解什么叫知识库、什么叫 collection、什么叫 embedding，只需要知道“把文档传进来，等处理完成后就能在聊天里挂载使用”。  
从底层实现上，它仍然可以有知识库、collection、向量索引这些概念，但前台不一定要全部暴露给用户。  
所以这其实是产品体验和底层架构解耦的一个例子。

# 21. 你简历里还有 WebSocket 实时聊天、小程序 AI 对话，你怎么把它和这个平台联系起来？

参考答案：
我会把它理解成两层。  
AI 工作台是偏后台和平台侧能力，重点是模型接入、文档中心、知识检索、会话和任务调度。  
小程序 AI 对话则是业务场景侧落地，重点是怎么把这些平台能力用到酒店、景区的具体业务里，比如在线客服、AI 讲解、反馈回复。  
这两者本质上是“平台能力”和“业务消费端”的关系。  
所以我在简历里同时放这两个项目，也是为了说明我不只是会接模型接口，还能把 AI 能力落到真实业务里。
