# 4. 你们为什么选 WebSocket 做 AI 对话？

参考答案：
因为这个场景不只是“服务端往前端推文本”，而是一个实时交互链路。  
模型需要流式输出，用户也可能主动停止生成，系统还要同步连接状态、会话状态、人工接管状态，所以需要双向通信。  
WebSocket 在这里比普通 HTTP 更适合，也比 SSE 更灵活。

# 5. 如果我问你，SSE 也能流式输出，为什么不用 SSE？

参考答案：
SSE 可以做单向流式输出，如果只是简单展示模型文本，它是够用的。  
但我们这个场景还需要客户端主动向服务端发事件，比如停止生成、重连恢复、状态同步，所以更适合双向通信的 WebSocket。  
所以不是 SSE 不行，而是 WebSocket 更匹配当前需求。

# 6. 你解释一下 RAG 的完整流程。

参考答案：
RAG 我一般分成离线和在线两部分。  
离线是文档上传、解析、切片、向量化、写入索引。  
在线是用户提问、问题向量化、检索相关片段、把问题和片段一起拼进 Prompt，然后交给模型生成答案。  
核心目的就是让模型在回答时引用外部知识，而不只是靠自己参数去猜。

# 7. 如果知识库没命中，你们怎么处理？

参考答案：
我会尽量避免把低相关度结果硬塞给模型。  
如果检索不到足够好的内容，可以走保守策略，比如提示当前知识库中没有足够信息，或者让模型在没有外部依据时明确说信息不足。  
企业场景里我会更偏保守，因为答不上通常比胡答更安全。

# 8. 你怎么区分“知识库问答”和“真正的 Agent”？

参考答案：
知识库问答的核心是“检索相关知识，再生成回答”，重点还是答问题。  
真正的 Agent 更强调基于目标去规划、调用工具、执行步骤并完成任务。  
比如只是回答制度问题，这更像 RAG；如果它能基于问题去查系统、建工单、调接口、回写结果，那才更像 Agent。  
所以我会说我做过比较扎实的 AI 工作台和 RAG 应用，但真正的 Agent 能力还在往工具调用和编排方向延伸。

# 11. 多业态接口口径统一是什么意思？

参考答案：
比如同样一个能力，不能只按 hotelId 去设计，因为景区端也要复用。  
所以会抽象成 ownerType 和 ownerId 这种更通用的设计，把“酒店”和“景区”都统一进来。  
这样后端底层可以复用，前端只需要根据当前业态传对应上下文。

# 14. 你们为什么要做 30 秒去重？

参考答案：
因为 NFC 触达很容易出现同一个用户短时间内连续碰多次的情况。  
如果全部按有效触达算，数据会失真。  
所以设计一个时间窗口去重，是为了让数据更接近真实用户参与行为。  
30 秒只是当前业务上比较合理的一个口径，本质是为了过滤误触和重复触发。

# 15. 这个去重逻辑为什么放后端？

参考答案：
因为前端不可靠。  
前端只能优化交互，不能作为最终统计依据。  
真正的活动口径要统一由后端判定，这样无论用户怎么刷新、重进、重复请求，统计标准都一致。  
对于运营看板来说，稳定的数据口径比前端展示更重要。
