## 一面版

### 开场与定位

1. 你先做一个 1 分钟左右的自我介绍，重点讲你为什么把自己的定位写成“全栈开发工程师（偏 Agent 应用方向）”。
    回答：面试官你好，我是蓝剑豪，本科专业是计算机科学与技术，目前主要做全栈开发这一套，技术栈的话前端偏向vue3和uni-app x，后端偏向springboot和fastapi。我这段时间做的项目主要在文旅板块和AI应用方向，
    一类是偏向落地的saas系统，有客小智，景小智，饭小伴小程序，以及对应的管理员后台。另一类的话是偏AI工作台和企业知识库的平台，涉及到流式对话、文档中心、RAG，本地和在线模型的接入。
    至于我为什么要把自己的定位写成全栈偏agent方向，一方面是我自己的优势，我可以把前后端 小程序 AI场景串联起来做完整交付 另一方面是 我也在往agent应用工程方向继续深入

    优化意见：少报框架名，多强调你的独特卖点。比如把重点落在“我不是单纯前端，也不是只会接模型接口，我更擅长把多端页面、后端接口、实时消息和AI能力串成一个完整可交付链路”。

2. 你这三段项目经历里，哪一段最能代表你当前的真实水平？为什么不是另外两段？

    从真实水平来看，那肯定是AI工作台项目，它覆盖了完整的前后端、RAG、模型接入、文档处理、Websocket，技术覆盖更全面，也对应的我的定位，偏agent应用方向

    优化意见：只能选一个。你现在更适合统一口径：AI工作台代表当前技术深度，NFC代表业务闭环能力，但如果只能选一个，我选AI工作台。 这样才稳。

### 主项目：AI 工作台与企业知识库平台

4. 你先整体讲一下 `AI 工作台与企业知识库平台`，不要堆功能，要讲清楚这个系统的核心链路。
    回答：好的，我来讲讲这个平台，这个平台主要是为了政企部门打造的平台，主要功能包括大模型对话，文档处理，OCR以及TTS，大模型对话的核心链路就是 用户提问，这个问题被向量化，然后到知识库中匹配对应的知识库向量，
    再将用户的问题和召回的知识库文本一起提交给大模型，由在线大模型或ollama中的本地大模型来进行回答，文档处理则是RAG，用户上传的文件，经过解析，向量，分块，入库后，等待用户提问，然后再进行向量匹配，召回。

    优化意见：以后这样讲：这个平台的核心不是功能清单，而是两条主链路：一条是对话链路，负责用户提问、模型选择、检索增强和流式返回；另一条是知识链路，负责文档上传、解析、切片、向量化和可检索化。 这样层次就出来了。

5. 你在这个项目里写了“参与 AI 对话、模型切换、会话管理和消息渲染开发”，这里面你实际做得最深的是哪一块？最浅的是哪一块？
    回答：我做的最深的是参与AI对话，就是用户提问发送给大模型，大模型回答后推送给用户，这里用到了websocket来保持连接，同时记录会话状态。最浅的是会话管理，因为只是简单记录了提问人 回答模型 会话seession等

    优化意见：如果你说自己最深的是 AI 对话，那就要补上你真正碰过的细节，比如消息协议、流式渲染、会话ID、模型参数、异常处理、重连、消息落库，至少要占两三个点。不然面试官会继续追，你会扛不住。

6. 一个完整的 AI 对话请求，从前端发起到页面上流式显示出来，中间完整经过了哪些环节？
    回答：完整对话请求，那我默认是带有知识库检索的能力，前端发起请求后，后端会调用向量模型，将用户提问向量化，再将这个向量后的提问去和处理好的知识库匹配，还有个召回率啥的，如果权重高，则将匹配到的文本内容和用户提问一起发送给大模型，由大模型来生成回答，最后流式推送给前端。如果权重底，则只会将用户提问发送给大模型，不会将知识库内容发送给大模型。

    优化意见：以后不要把“完整对话链路”答成“完整RAG链路”。这题更好的结构是：前端发消息 -> 带上会话信息和模型信息 -> 后端校验与加载上下文 -> 判断是否走知识库 -> 检索与拼Prompt -> 请求模型 -> 流式返回 -> 前端增量渲染 -> 会话与消息落库。

7. 你们为什么要做“模型切换”？这个能力落到前后端分别意味着什么？
    回答：模型切换目的在于让用户选择更适配的模型，如果用户提问简单的问题，那就可以调用更轻量化 参数更少的lite模型或flash模型，如果用户的问题涉及到数学/编程/总结等要求，那当然还是参数量大的完整模型，如我们现在调用的deepseek-v4-pro，此外，如果用户不希望数据上云，那也可以切换为本地模型，算力都在本地，更私密更安全。这个能力落到前端意味着用户能通过下拉菜单/搜索框找到适合自己的模型。落到后端，则意味着要根据前端传来的参数路由到不同的模型，由对应模型完成用户回答。

    优化意见：把“前端是下拉框选择模型”这种太表层的话收一收，更多往系统设计上答。比如前端要维护“当前会话绑定的模型配置”，后端要做“模型路由、参数适配、能力兼容和错误兜底”。这样更工程化。

8. 会话管理你是怎么理解的？它和“只是把聊天记录展示出来”有什么本质区别？
    回答：我理解的会话管理，就是能够在后台管理会话，可以看到用户提问/模型回答等，有助于优化提示词，使大模型的回答更符合用户想要的答案。它和把聊天记录展示出来的本质区别，这我还真不懂，复盘的时候你得帮帮我

    优化意见：你必须补这个点。会话管理的核心是“上下文边界和状态组织”，不是“聊天记录查看”。本质区别在于：聊天记录展示只是UI层结果，会话管理涉及会话ID、上下文归属、消息顺序、模型绑定、状态恢复、历史追溯、继续提问时带哪些上下文。这题不补，后面一追就穿。

9. 文档上传、解析、切片、向量化、检索，这条 RAG 链路你按离线和在线两个阶段分别讲一遍。
    回答：离线端，就是文档上传，解析，切片，向量化，写入索引。在线端则是用户提问，问题向量化，检索相关的片段，再把问题和检索到的片段拼接到prompt里，交给大模型来生成答案。本质就是不让大模型引用外部只是，而不是只靠模型参数来猜用户的问题

    优化意见：在你现有答案上补一句就会更稳：离线阶段是把原始文档变成可检索知识，在线阶段是按用户问题动态取相关知识，而不是把整份文档全塞给模型。 这样会更像你自己真的理解过。

10. 你们做知识库问答时，为什么不能简单理解成“把文档丢给模型”？
    回答：有几个原因导致的，一个是，把文档丢给模型，那和直接把文案内容复制出来变成prompt没有区别。二是，如果文档内容很大，不做向量处理，那一个文档可能就会塞满整个上下文，造成用户提问失败或大模型没有记忆的情况。三个是，如果知识库中有内容冲突，那大模型就没有办法根据用户的问题来匹配答案，最后只能是胡乱回答，造成模型幻觉。

    优化意见：把原因压成三句就行：一是上下文窗口有限，二是整文塞进去成本高且无关信息多，三是模型需要按问题动态取相关知识而不是盲读全文。 这样更干净。

11. 向量检索和关键词检索有什么区别？如果召回效果不好，你会优先怀疑哪几个环节？
    回答：向量检索就是召回率吧？然后关键词检索是从向量中拿到关键词，再分析上下文？这我还真没了解过。召回效果不好我会怀疑下面几个方面，一是分块策略的问题，如果用户提问的向量匹配到一个分块底部，那就只会拿到当前chunk的内容，下一个分块的内容就没办法获取，造成召回效果不好，是这样吧？？第二个就是   我也不知道第二个还有啥了，这你得帮我

    优化意见：这个必须硬补。最基本要能说：关键词检索看词面匹配，向量检索看语义相似度。 召回效果不好时，至少要能怀疑 切片策略、embedding模型、检索参数、重排策略、文档质量 这几层。你现在只答出 chunk 一层，远远不够。

12. 你简历里写了 `OpenAI Compatible API`，这个概念你怎么理解？它对工程接入的价值是什么？
    回答：我理解起来就是兼容Openai格式的api返回数据，价值就是标准化，只要参照这个格式，收到的json格式都是一样的，不用额外适配

    优化意见：以后至少答成：OpenAI Compatible API 指的是接口协议兼容 OpenAI 的调用方式，包括请求体、消息结构、流式返回格式等。工程价值是可以用统一 SDK 和统一代码路径接不同模型服务，降低切换和接入成本。

13. 你们为什么用了 `WebSocket`？如果只做普通聊天问答，`SSE` 能不能做？你怎么选？
    回答：用websocket主要是为了双向同步信息，即用户端能及时收到大模型的流式消息，SSE也可以做，但是效果肯定没有Websocket那么好，因为SSE是单向通信，也就是服务端推送消息，如果只是简单的展示模型生成内容，那SSE够用，但是我们这个场景还需要用户端向服务端发送事件，比如重连，停止生成，状态同步等，所以更适合用websocket

    优化意见：把绝对化说法改掉。更稳的说法是：如果只是服务端单向流式输出，SSE就够用，甚至更轻；但如果还要双向事件交互、状态控制和会话同步，WebSocket更合适。

14. 会议转写、文档转换、TTS 这些本地任务模块，你主要参与的是哪一段？如果这些任务执行时间长，前端怎么感知状态变化？
    参考答案：这一块我更适合按真实参与情况来讲。我主要参与的不是底层转写模型或者TTS引擎本身的实现，而是这些本地任务在平台里的接入和联调，比如任务发起、任务状态展示、结果回显，以及和对话、文档中心这些模块之间的衔接。如果这些任务执行时间比较长，前端一般不能一直傻等一个接口返回，而是要有任务状态机制。比较常见的做法是，用户发起任务后，后端先返回一个任务id和初始状态，比如排队中、处理中、已完成、失败。前端再通过轮询或者WebSocket去拿最新状态，这样用户能看到任务是否还在处理中，完成后也能及时拿到结果。所以这一块我会更强调自己做的是任务接入、状态流转展示和前后端联调，而不是去把底层语音模型或转写模型说成自己主导实现。

15. 这个项目里你最容易被问穿的一个点是什么？如果面试官继续追，你会怎么把它讲实？
    参考答案：如果要我自己说，这个项目里我最容易被问穿的点，其实是知识库检索和会话管理更底层的那部分实现细节。因为我确实参与了这条链路的联调和功能落地，也理解完整流程，但是像embedding模型怎么选、切片策略怎么调优、召回参数怎么压、重排怎么做，这种更底层的策略设计并不是我主导的。如果面试官继续追，我不会硬扛成“这些都是我设计的”，而是会把边界讲清楚：我真实参与的是AI对话链路、模型切换、消息渲染、文档上传和知识库联调，也知道RAG离线和在线的完整流程；但如果追到特别底层的检索调优或算法策略，我会明确说这是我理解过、接触过，但不是我主导设计的部分。我觉得这样讲反而更真实，因为比起把所有东西都说成自己做的，能明确说清楚“我做了什么、理解到哪一层、哪一层不是我主导”，会更容易让面试官相信前面讲的内容。

## 使用建议

- 第一遍自测：只做 `一面版`，每题限制在 `2 分钟` 内。
- 第二遍自测：做 `压力版`，专门练“被怀疑时还能不能讲实”。
- 第三遍自测：随机抽题，不允许按项目顺序答，训练切换能力。
- 如果你答题时经常出现“这个我项目里是别人做的、我主要是联调”，那就说明这块不能包装成主卖点。
