# AI 使用说明

本文对应交付要求中的“4. AI 使用说明”，重点记录本项目用了哪些模型与工具、分别做了什么，以及 AI 产出在真实开发过程中出现了哪些问题，最终如何修正。

## 1. 使用的 AI 与工具

### OpenAI Codex（GPT-5）

主要用途：

- 根据题图拆解功能边界和交付要求。
- 生成 Electron 主进程、preload、React 界面和基础样式代码。
- 设计数据结构、IPC 协议和 Claude CLI 流式解析流程。
- 在排障阶段持续读取日志、比对配置、补充诊断能力。
- 最终整理设计说明、AI 使用说明和 README。

### 图片查看与本地检索工具

主要用途：

- 读取题图，提取大题要求和交付清单。
- 读取日志文件、状态文件、用户级 Claude 配置文件。
- 用 `rg`、`sed`、`git diff` 快速定位实现与真实问题。

### Claude Code CLI

它不是本次写代码的 AI 生产者，而是这个桌面应用的运行时依赖。也正因为它是真实依赖，所以后半程大量问题都必须围绕它的真实行为来排查，而不能只靠代码静态分析。

## 2. AI 在本项目中的分工

AI 主要参与了四类工作：

### 需求拆解

先从题图里抽出最小闭环，不额外加需求，只保留：

- 聊天
- 切模型
- 多会话

### 初始实现

AI 负责先把最短路径搭出来：

- Electron 主进程拉起 `claude`
- preload 暴露白名单 API
- React 渲染会话、消息、输入区、设置弹窗
- 用 JSON 存储会话与设置

### 文档编写

AI 负责把实现整理成可交付材料，包括：

- 设计说明
- AI 使用说明
- README 与演示说明

### 运行期排障

这部分是本次最有价值的 AI 使用场景。问题并不是“代码不会写”，而是“代码能跑起来后，真实系统为什么不按预期工作”。AI 在这里的作用更接近一名持续读日志、对比配置、迭代假设的调试助手。

## 3. AI 产出中出现的问题与修正

下面这些问题都是真实出现过的，且已经反映到当前代码和文档中。

### 问题一：初版错误提示过于粗糙

最开始界面只显示“Claude Code 退出，状态码 1”。这类错误对定位几乎没有帮助，既不知道是认证失败、模型不支持、还是 CLI 配置污染。

修正方式：

- 给 `claude` 子进程增加独立的 `--debug-file`。
- 把 stderr 原文和日志路径一起回传到界面。
- 解析失败时把原始输出片段也附到错误里。

结果：后续每次失败都能拿到明确日志，不再靠猜。

### 问题二：把“能列出模型”误判成“能正常发消息”

服务商配置页能成功请求 `/v1/models`，一开始容易误以为整条调用链已经通了。后来发现，模型列表查询成功，只说明普通 HTTP 请求能通，不代表 `claude` CLI 真正发消息时也会按预期走这套服务商配置。

修正方式：

- 把“查模型”和“Claude Code 真发消息”明确当成两条链路来排查。
- 单独给发送链路补日志，而不是只盯着服务商配置页。

结果：很快区分出“模型列表没问题，真正坏的是 Claude CLI 运行时环境”。

### 问题三：默认模型别名和服务商模型列表不一致

会话初始模型是 `sonnet` 这类别名，但服务商返回的真实模型列表里未必有这个值。结果是 UI 看起来能发，实际传给 CLI 的模型可能无效。

修正方式：

- 渲染层发现当前模型不在当前服务商模型列表中时，自动切回首个可用模型。
- 主进程发送前再做一次硬校验，不允许无效模型进入 `ClaudeRunner`。

结果：模型状态和服务商配置重新对齐，不再出现“界面一个值、实际发另一个值”的情况。

### 问题四：一开始把认证问题理解得过于简单

早期判断是“环境变量名可能写错”，于是先把 `ANTHROPIC_AUTH_TOKEN` 改成了 `ANTHROPIC_API_KEY`。这一步并不算错，但事实证明它只解决了表层问题，没有解决真正的环境优先级问题。

修正方式：

- 先根据 `claude --help` 修正 API key 变量写法。
- 再通过日志验证 CLI 实际使用了哪类认证。
- 发现仅靠改变量名仍不足以隔离本机现有登录态。

结果：定位思路从“静态猜测”升级成“看 CLI 真正怎么跑”。

### 问题五：`--bare` 也没完全隔离掉本机配置

即使加入 `--bare`，日志里依然出现 `OAuth token check` 和 `dispatching to firstParty`。这说明 Claude CLI 仍然被别的本地配置污染。

修正方式：

- 继续读取本机 `~/.claude/settings.json`。
- 发现里面写死了 `ANTHROPIC_AUTH_TOKEN`、`ANTHROPIC_BASE_URL` 和默认模型。
- 在启动参数里追加 `--setting-sources project,local`，直接跳过 `user` 级设置。
- 在子进程环境里主动删除继承到的 `ANTHROPIC_AUTH_TOKEN`。

结果：桌面应用对 Claude CLI 的调用终于与本机用户全局配置解耦。

### 问题六：文档和实现发生了漂移

项目演进后，README 与早期设计文档里仍然写着“认证沿用本机 CLI 登录状态”“不保存 API Key”，这已经和当前真实实现不一致。

修正方式：

- 重写设计说明，明确当前是“服务商配置 + 加密存储 Key + 主进程注入环境变量”的方案。
- 重写 AI 使用说明，把这次对话中的真实问题与修复过程沉淀进去。
- 同步修正 README，避免交付材料互相矛盾。

结果：交付文档和代码行为保持一致，不会出现“代码一套、说明另一套”的问题。

## 4. 人工介入与最终兜底

AI 帮助非常大，但真正让项目闭环的是人工对以下事项的持续确认：

- 所有结论都必须由日志、配置文件或代码路径支撑，不能只靠语言模型猜。
- 每次只收敛一个变量，例如先补日志，再确认模型，再确认认证，再确认用户级配置污染。
- 文档必须跟着实现一起更新，否则交付阶段会被自己早期的说明反噬。

本次最典型的经验是：AI 能大幅加快实现和定位，但当问题进入“本机环境、CLI 行为、配置优先级”层面时，必须把证据链补齐。没有日志，AI 再聪明也只能猜；有了日志，AI 的价值才真正体现出来。
